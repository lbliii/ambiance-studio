# Studio plan alignment: workflows, reusable models and films

Updated September 13, 2026 for second-wave integration based on merged main `71aa947`. This is the integration map for the existing plans, not another task backlog, runtime schema or implementation claim. Each linked owner below retains its statuses and acceptance criteria. The Amberwatch audit supplies observed failures; it does not create a competing feature program.

## Intended product

The product direction is **agent-operated traditional animation**: agents carry out production under human creative direction, using familiar animation conventions and persistent editable art, performances and timelines. The [vision and epic mapping](AGENT-ANIMATION-VISION.md) records the September 13 clarification, multimodal responsibilities and new acceptance outcomes. Text/reasoning, image generation, audio and visual understanding support authored animation; generated video is an optional scoped source/reference.

An agent should be able to start from a script, storyboard or seed, account for the whole scene, find or prepare complete editable models, compose instances, direct picture and sound, inspect exact results and return accepted reusable work to the library. Ambiance loops and finite narrative films share art, evaluation, evidence and delivery foundations. Their chosen duration, formats and story requirements remain explicit.

Two developments make this practical. **Workflow guidance** connects actual project state to usable operations and explains their inputs, results and repair paths. **Reusable models** provide editable definitions, nested assemblies, independent instances, compatible controls/variants and versioned reuse. Good guidance cannot manufacture an absent model operation; a model operation is not useful if an agent never discovers or applies it.

Existing source preparation, registered placement, sockets, tracks, bindings, rendering and evidence are reusable foundations. They do not already constitute the proposed workflow or model system. A flat source-separation recipe is useful for a shared reference/backing problem; it is not a mandatory wrapper for already-isolated artwork. A compiled raster is not automatically an accepted editable model.

## Shared decisions to resolve once

1. **Scope and technical ownership.** Canonical plan/inventory own scene requirements and fulfillment. Model definitions/instances will own technical assembly and allowed overrides. Workflow references these authorities. A planning packet or model checklist must not become another editable census.
2. **Stable identity and explicit updates.** Align model, character, part/drawing, nested dependency, instance and variant identities before their consumers implement incompatible contracts. Pin accepted versions; adopting a new definition or incompatible override is explicit and reviewable. Generated raster layers and masks must not become an independently edited second source of truth. The initial technical choices and specimens are in [mc/1](model-contract/contract-v1.md); implementation schemas and full Phase 1/P00 acceptance remain separate.
3. **Coordinates and time.** Reuse source/compiler mappings, local frames, pivots and sockets. Distinguish registration from scene placement. Model controls consume the shared evaluated clock; P03 owns finite-shot/local-cycle conversion and legacy-loop compatibility. Model reuse must not silently inherit an originating film's canvas, duration or fps.
4. **Ownership, mounting, draw order and light.** These remain distinct. A lantern owns its candle/flame/front frame and mounting keeps them together; a light contribution belongs on its receiving ground. Moving or hiding a source must affect the intended contribution without moving the ground or removing other illumination. Selection/grouping must not silently reparent or reorder paint.
5. **Derived products and evidence.** Composite alpha, material/solid masks, silhouettes and bounds describe a specified model pose/variant and dependency set. Proofs identify actual selected/hidden parts, instance overrides, view and time. Reuse the existing renderers and evidence validators; add typed adapters where needed. Alpha/geometry/hash checks cannot identify a lantern baked into planter RGB or establish finished hidden paint.
6. **CLI and browser authority.** Native operations own validation, transactions and recovery; browser editing and inspection use the same semantics. Workflow prepares native inputs and points to real commands. It does not execute arbitrary scripts or expand model internals itself. Use the extracted command adapters and explicit output ownership; preserve existing envelopes and error behavior.
7. **Library boundaries.** Film discovery, editable visual-model reuse and sound-source reuse have different records. Share version/provenance principles and safe project materialization, not an overloaded raster schema. Second-scene reuse must work without the first scene's mutable directory, while preserving its accepted version.

The [coordinated restart](COORDINATED-IMPLEMENTATION-2026-09-13.md) names the integration owner and links the model Phase 1/P00 technical packet. Register any shared-file work explicitly against the then-current modules. This coordination is a bounded prerequisite for dependent implementations, not a new project-wide permission gate or a reason to delay independent story, existing-asset or workflow work.

## Shared acceptance cases

Use one supplied-art integration experiment across the workflow and model plans. Build or find a complete lantern with a nested candle/flame, expose a small compatible control/variant set and instantiate it twice. Move, mount, hide and vary one independently. Put a pumpkin in front, then hide it to reveal complete lantern paint. Hide the lantern and inspect all contributing layers and its ground-light response. Inspect flame/front-frame occlusion at extremes, transparent/solid role masks and contacts in both intended compositions. Save/reload, interrupt/resume, reject stale dependencies and verify explicit version adoption. Retrieve the accepted model from its library for another composition.

Broaden with materially different art: a tree/environment family and a complete character. A two-lantern engineering fixture cannot establish whole-scene reconstruction, artistic suitability, general model behavior or the full-minute narrative result. Selected full-film requirements stay required.

For narrative adoption, also demonstrate familiar animation authoring, actual visual/listening review, a scoped directing revision and character reuse in another shot. Exposure sheets describe the canonical evaluated tracks; model observations identify exact inspected frames/audio and remain separate from measurements and human verdicts. The [vision](AGENT-ANIMATION-VISION.md) maps these added criteria onto existing film milestones; their statuses remain with the roadmap and package owners.

For the operator trial, record the actual operation selected, any demonstrated capability mismatch before custom mechanics, correction attempts and what pixels/playback were inspected. Test both a source-backed separation task and already-isolated art. Include an opaque-checkerboard case requiring an explicit candidate matte so the trial allows justified gaps. Reading a skill, reducing call count or successfully encoding a movie cannot pass the reuse/observation criterion. The preserved planter-lantern, unattached-flame, tree-sky and pumpkin-rock cases must be detected in their relevant proofs.

Independent bounded improvements such as alpha heatmaps or exact-backend benchmarks may ship through current owners. They do not need to wait for the model system, and they must not be presented as solving semantic ownership or lighting appearance by themselves.

## Operator guidance now and later

Use shipped commands today. Before introducing project-specific production mechanics, identify the closest supported operation and inspect or probe its suitability; record a concrete uncovered behavior before a workaround. Keep artistic decisions in native data. Do not force source separation where isolated art already exists or claim a proposed model command is available.

This immediate safeguard belongs in the short shared guidance. WF-07 owns adoption of the proven guided entry point and any default-output change after WF-06. Skills retain creative methods, useful examples and judgment; they should not grow a second operational stage checklist. Guidance uses current exact state, never infers acceptance or provider authority, and keeps independent work visible while human observations remain open.

## Validation and change control

No runtime capability, movie acceptance, provider budget or task dispatch is created by this document. Planning changes validate links, task/dependency references, status preservation and package/skill structure. Shared implementation changes run the repository suite and affected native/browser tests. Those checks remain distinct from fresh-operator and artistic trials.

Update the owning plan when scope, status or acceptance changes; update this map only when their integration changes. A findings document may add evidence but should not duplicate task statuses. The whole-scene, second-scene and full-short outcomes stay visible even when a component prototype succeeds.
